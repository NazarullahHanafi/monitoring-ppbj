# Attachment search hint transfer budget — 19 November 2026

The SP/SPPH list selected every matching reviewed attachment's complete text to build its hints, then discarded later matches for the same document in PHP. For ten displayed documents with five matching attachments each, fifty large texts crossed the database boundary even though the interface displayed ten snippets.

`ProcurementDocumentSearch::attachmentHints` now selects the earliest matching reviewed attachment ID for each displayed document using a correlated scalar subquery. Its `LIMIT 1` applies per document after the complete reviewed text and existing literal token predicates are checked. The outer query retrieves only these selected files, still in one SQL statement. There is no global limit that could hide another displayed document, no extra round trip, and no window-function/version requirement. The parent IDs originate from the already selected page; table names originate from the SP/SPPH flag. Existing parameter binding, wildcard escaping, review requirements, kind separation and snippet normalization remain intact.

Files with equal creation timestamps now use their ID as a deterministic tie breaker. Older results did not specify a tie order, so the representative filename/snippet may change for an exact timestamp tie. Search membership and non-tied representatives remain the same. All reviewed attachments remain eligible for matching, including a later file when earlier files do not match. The change bounds representative text transfer; it does not truncate the searchable source text or alter OCR extraction, review, index synchronization, download authorization or export filtering. No business-state cache is added.

Five new regression tests observe the raw result-row/text-byte counts through the database processor before PHP snippet construction. They cover both SP and SPPH, fifty matching files on a ten-document page, first matching versus first unrelated/unreviewed file, off-page/kind/draft exclusion, deterministic timestamp ties, deep Unicode text, literal `%`, `_`, `!` and `0`, hostile SQL-like input, bounded UTF-8 snippets, current review/delete changes and zero SQL for empty inputs. The old implementation failed three tests. The focused search/attachment/filter set passes **85 tests / 1,249 assertions** and the complete PHP suite passes **1,052 tests / 11,947 assertions**. Pint passes for the helper and new test file. A few existing compact control statements in the same helper were formatted without changing behavior.

A fresh-process benchmark uses isolated in-memory SQLite with ten synthetic SPs and five 192,011-byte reviewed texts per SP. It compares the actual helper from baseline commit `ee84e321da1b2197291504daca8754ef2808df1d` with the candidate. Both produce the same ten hints and output SHA-256 with **one SQL query**. Transferred text decreases from **9,600,550 bytes in 50 rows** to **1,920,110 bytes in 10 rows**. Additional PHP peak memory above the pre-call baseline decreases from **10 MiB to 2 MiB**, about **80%** in this workload. This is representative-hint memory/transfer work, not total PHP/database process memory, OCR speed, all searches or whole-site latency.

A read-only production EXPLAIN check independently confirms that the installed MariaDB accepts the scalar query and uses a primary-key range for the ten parent IDs, an `eq_ref` primary-key lookup for selected attachment text, and an existing attachment index for candidates. Candidate/deployed probes compare bounded real SP/SPPH samples with the prior helper for membership, non-tied snippets, query counts and transferred row counts. Exact timestamp ties are explicitly accounted for. Samples are reduced if their total reviewed text exceeds an eight-MiB probe budget, and only aggregate counts/plans are printed. A sample without reviewed attachments cannot demonstrate an actual transfer saving; the synthetic benchmark covers the multi-attachment workload.

Deployment is restricted to the helper, regression test and this document. Modified source and bootstrap cache are backed up privately before the fast-forward. Production probes use a read-only transaction, array cache/session, prevented external HTTP and zero business writes. No archive file is uploaded, downloaded, modified, deleted or reprocessed. Source hashes, health/authentication checks and a clean tracked tree are verified after deployment. No migration, asset publication, dependency change, cache rebuild or global cache flush is needed.
