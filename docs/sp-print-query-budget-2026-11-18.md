# SP printing query budget — 18 November 2026

Every normal SP print read its item rows twice: first at the public renderer entry, then in the selected SP/contract template. Each of the three contract value tiers additionally queried its primary PR once for dates/references and again for the general registration note. Vendor and primary-PR lookup queries hydrated complete models although the templates used a small subset of columns. These repeated reads were confirmed by four failing query-budget regression cases and by a read-only production baseline with synthetic documents.

The public `cetakSp` entry still refreshes the item relation from the database. Subsequent template reads use `loadMissing`, so the same print operation reads items once. Direct lower-level template calls can still load an absent relation. All four templates now share one trimmed primary-PR lookup selecting only identity, relevant dates, SPPH/winner references and general registration metadata. Contract registration notes reuse that loaded PR instead of issuing another query. Vendor lookup selects only identity, address/contact, NPWP and signatory details, while retaining the exact-match-first behavior and legacy case/whitespace fallback. Historical inactive vendors remain printable as before. No cross-request cache of document contents is introduced.

The measured query budgets are **one item read per print** instead of two at all four value tiers, and **one primary-PR read per contract** instead of two. Normal SP printing saves one query; each contract saves two. These budgets exclude distinct policy validation, linked-PR labels, master lookups and vendor fallback; they are not total request-query counts or a percentage latency claim. Empty vendor/PR references issue no lookup SQL. Reads of vendor and primary PR no longer use `SELECT *`.

Six new feature cases cover the four actual DOCX renderers, an intentionally preloaded stale item relation, current item contents, general registration number, vendor address/director, PR number, selected field, realization payment text, XML validity, query counts, projected fields, empty references, historical vendor matching and fresh PR metadata across successive lookups. Existing payment tests cover both payment modes in all tiers, inactive master rejection, invalid payment before SQL, preview metadata and read-only confirmation. Existing print/bidang/kop tests also pass. The focused run passes **26 tests / 277 assertions**. The full suite passes **978 PHP tests / 10,863 assertions** and **618 JavaScript tests**. Browser payment checks pass desktop/light and mobile/dark for both modes, retaining drafts, no write on Cancel, one explicit confirmation, no extra reads while changing payment choice and same-tab preview navigation.

Production verification runs the old baseline and staged/deployed code with synthetic, unsaved SPs at an unused ID/reference under a read-only database transaction. Cache/session drivers are process-local arrays and outbound HTTP is blocked. Eight temporary DOCX files per run cover four tiers and both payment modes. Their ZIP/XML and payment/reference text are checked, then each is removed only after validating its exact synthetic filename and private storage directory. No actual SP, PR, vendor, account or approval is modified and no audit row is created. Authentication/department route guards and public health checks are verified separately.

Deployment requires the exact prior commit, a three-file allowlist, private controller/bootstrap-cache backup, PHP syntax checks, a staged probe before fast-forward, a deployed probe and controller hash verification. No public asset, view, route, dependency, schema or shared cache flush changes are required. Existing unrelated untracked user artifacts are excluded. Document layout and payment/signing rules are preserved; this is a targeted print-path reduction in database work, not a claim that every site operation is now free of defects or latency.
