# Procurement attachment dialog guards — 18 November 2026

The shared SP/SPPH attachment dialog previously waited for delete or unsaved-text confirmation before claiming its busy state. Repeated invocations could open multiple confirmations. Opening another document could replace the current dialog's state and the parent form's pending save decision. Buttons retained from a replaced attachment list could still invoke obsolete callbacks. A successful review response only needed a matching ID and newer reviewed version; different returned text could clear the user's correction.

The dialog now owns its controls before awaiting either confirmation. Cancelling or failing a confirmation releases that ownership and retains the draft. An open dialog cannot be replaced, and another parent-save attempt returns false without replacing the original pending decision. Review/delete callbacks require the same dialog state, current connected attachment element, an open dialog and management permission. Closing releases the current state after resolving the original decision.

Review acknowledgment additionally requires the exact submitted text after PHP-compatible boundary trimming. Until then, corrections remain in the textarea and draft map. Attachment DTOs require a boolean reviewed flag, positive safe-integer version and three usable same-origin HTTP(S) URLs without embedded credentials or fragments. Requests enforce the same URL boundary before sending CSRF-protected credentials and use `cache: no-store`. A complete list requires typed permissions/number, valid attachment DTOs and unique IDs before replacing any current data. Failed initial reads show an unavailable list rather than falsely reporting no attachments; a successful explicit refresh can restore the controls.

The form's mutation observer now attaches only to an existing item-row container, and status text is only rewritten when its message changes. Previously its fallback observed the attachment status component itself, while its callback rewrote that component's text. Without a row container, this produced a continuous mutation/update loop. The browser fixture intentionally omits that container and exercises normal form initialization and all dialog flows. Input events still update attachment hints, and existing row containers retain their mutation observer.

Verification: **618 JavaScript tests** and **972 PHP tests / 10,785 assertions**. New unit tests check URL/CSRF/cache boundaries, DTO types and atomic list validation. Actual browser scenarios run on desktop and mobile using the real FormUX confirmation dialog: repeated close/delete attempts, cancellation, a failed confirmation, another document opening, disconnected old callbacks, wrong review text, one in-flight DELETE, preserved corrections, parent-save completion, failed/malformed lists and explicit recovery. Existing attachment recovery, version-conflict and stalled-body scenarios pass. Actual native-PDF and scanned-PDF reading plus immediate versioned confirmation also pass without external document requests. Screenshots were inspected.

Deployment uses the exact previous commit, a four-file allowlist, private application/bootstrap-cache/public-asset backups, staged and deployed read-only probes, atomic public JavaScript publication, HTTPS asset hash verification, health checks and an unauthenticated attachment access check. Probes use an unsaved synthetic actor, array cache/session, blocked outbound HTTP and a read-only SQL transaction. They check the unchanged server DTO, original/reviewed text, versions, same-origin URLs, privacy/access guards and existing SP/SPPH list reads, each using five SELECTs. No real attachment is created, reviewed or deleted by the probes.

This batch changes one shared client workflow. It introduces no schema, backend query, route, dependency, polling, automatic write retry or global cache flush. Existing timeout messages still instruct users to reload and inspect an uncertain result; this is not an exactly-once upload guarantee or a claim of site-wide latency improvement. Draft preservation lasts while the dialog remains open and does not persist across page reloads. Backend authorization/version checks remain authoritative.
