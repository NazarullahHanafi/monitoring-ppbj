# Archive download streaming — 19 November 2026

The archive gateway validated its initial signed URL but let the HTTP client follow later redirects without checking their destinations. Production archive source inspection confirmed that remote attachments legitimately redirect to OneDrive. Blocking all redirects would interrupt that workflow.

The gateway now checks every resolved redirect before another request is made. It accepts the configured archive origin under `/api/archive/`, or HTTPS on port 443 under the same Microsoft domain boundaries already used by vendor downloads: `sharepoint.com`, `1drv.com`, `1drv.ms`, `onedrive.com`, `live.com` and `microsoft.com`, including their subdomains. User information in URLs, raw control characters/backslashes, unexpected ports and lookalike domain suffixes are rejected. Initial links must still use the configured archive origin; Microsoft links are allowed only after the authenticated archive request. Initial archive paths additionally reject decoded dot segments, control characters and backslashes. This is a destination boundary, not protection against a compromised permitted service or its DNS.

Streaming retains 256-KiB reads, a five-second connect option, a 300-second request timeout and a maximum of five redirects. A new 15-second read timeout bounds stalled reads in the installed Guzzle stream handler. The loop stops if PHP detects a disconnected client, and an empty read before EOF terminates instead of repeatedly reading without progress. Upstream bodies are explicitly closed both after streaming and after setup/status failures. HTTP 416 from a ranged request is returned as 416 with a validated `Content-Range`, without reading or forwarding the upstream error body. Successful 200/206 bytes and range/validator headers remain intact, including a zero content length.

Read failures are logged with their exception class and bytes already sent; connection/setup diagnostics omit exception messages containing signed URLs. A read exception after headers are sent cannot change the status or undo bytes already delivered. The gateway therefore closes the stream without appending an application error page to the file. Where a content length is available, the browser can detect the short transfer. Without one, clients may receive a truncated file and should retry; this change does not promise automatic completion or add hidden retries. Client-disconnect detection also depends on PHP and proxy buffering.

Download filenames remove actual control characters, and their ASCII fallback replaces percent signs so valid names such as `réalisasi 100%.pdf` remain downloadable. The UTF-8 disposition keeps the intended filename. Authorization, archive metadata caching, signed-link lifetimes and private/no-store headers remain in place. There are no schema, JavaScript, asset or write-flow changes, and the gateway adds no SQL or external metadata lookup.

Twenty-five new regression cases use the real Guzzle redirect middleware with an offline `MockHandler`, rather than assuming HTTP facade fakes exercise redirect following. They cover nine blocked destinations, an unsafe later hop after OneDrive, a valid archive→SharePoint→OneDrive chain, unchanged range bytes, bounded chunk sizes, read timeout options, early body closure, 416, mid-stream failures/empty reads, redacted diagnostics, zero-length files, Unicode/percent filenames and unsafe initial links. The original implementation failed the first sixteen regression cases. The focused archive/search/download set passes **100 tests / 1,706 assertions**; the full PHP suite passes **1,028 tests / 11,751 assertions**. Pint passes for the two changed PHP files.

A separate local loopback HTTP fault-injection check sends one synthetic PDF prefix and then deliberately holds the connection idle. The installed HTTP transport stopped after **15.12 seconds**, with one request, a closed connection and only the original sixteen-byte prefix in the output. It is not an internet throughput or whole-site latency benchmark.

Deployment is restricted to the gateway controller, regression test and this document. Application/cache backups precede the fast-forward. Candidate and deployed production probes use synthetic metadata and offline Guzzle handlers, array cache/session and a read-only SQL transaction with zero business writes. They check redirect rejection before a second request, byte parity, read faults, stream closure, range handling, configured archive-origin compatibility and authorization before metadata. No production file is uploaded, downloaded from OneDrive, modified or deleted by the probes. Source hashes, health/authentication checks and a clean tracked production tree are verified after deployment. No global cache flush, migration or cache rebuild is needed.
