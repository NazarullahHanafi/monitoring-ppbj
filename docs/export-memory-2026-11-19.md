# SP/SPPH export memory — 19 November 2026

The shared export generator kept its previous 200-document collection alive while fetching and hydrating the next batch. For SP this also retained the completed batch's eager-loaded item descriptions. Although exports already used keyset batches, two populated batches could overlap in memory. SP additionally loaded item fulfillment dates and timestamps that the CSV never uses.

`ProcurementExportRows::rows` now records the batch count and releases the completed collection and loop variable before reading another batch. The scalar cursor remains intact. SP's item eager load projects only `id`, `sp_id`, `urutan`, `nama_barang`, `satuan`, `jumlah`, `harga_satuan` and `subtotal`. The relationship key and ordering are preserved. Batch size stays 200; there is no OFFSET, new query, schema, client dependency or automatic retry.

Two regression tests reproduced the faults on the previous version. Weak references observed 200 completed models remaining alive at each transition, and the actual SP CSV hydrated eleven item fields. The fixed tests observe at most the final yielded model at the next batch's first retrieval and eight required item fields. Four added tests also cover ordered traversal with tied sequence numbers, eager items, identical query counts, CSV formula protection and stripped markup, early termination without prefetch, releasing a closed generator, exact 400-row boundaries and rejecting unsupported ordering.

The final full PHP suite passes **1,003 tests / 11,620 assertions**. The focused set passes **36 tests / 872 assertions**, including export/filter/search behavior, private preview ownership/signatures/expiry and vendor transfer/download protections. Pint passes on the three changed PHP files. There are no JavaScript, view, route or permission changes in this batch.

A fresh-process local benchmark compared the actual prior and candidate SP export controllers using in-memory SQLite and 425 synthetic SPs with one substantial item each. Both produced the same **17,083,915-byte CSV and SHA-256**, using six SQL statements while streaming (three document and three item reads). Additional PHP peak memory above the pre-stream baseline decreased from **20,482,048 bytes (19.5 MiB)** to **10,609,384 bytes (10.1 MiB)**, about **48%**. Retained completed models changed from `[200, 200]` to `[1, 1]`. This measures this synthetic streaming workload, not total PHP process memory, all website latency, database server memory or proxy/browser buffers. Callers deliberately retaining yielded models can still increase their own memory use.

The production baseline independently reproduced the 200-model retention on 425 real SPs and 425 SPPHs. Document order/membership and query budgets were checked without logging record contents or identifiers. SP item reads in the memory probe are enabled only when their aggregate text is within an eight-MiB probe budget. A separate day/PIC sample of at most twenty documents compares actual CSV bytes against a private reference controller extracted from exact baseline `e724fe125a04b679646a710332d7de461a079e1a`. Output is hashed incrementally rather than retained as a complete CSV. Candidate/deployed checks require byte parity, the narrowed projection when items exist, at most one retained model at transitions, unchanged query counts and download authentication guards.

Deployment is restricted to the export helper, SP controller, feature test and this document. Modified application files and bootstrap cache are backed up privately; staged lint/probes precede the fast-forward. Deployed probes, exact source hashes, health/authentication checks and a clean tracked tree follow. Probes use an explicit read-only SQL transaction, array cache/session, prevented external HTTP and zero business writes. No migration, asset publication, global cache flush or production document generation is involved. The per-batch memory reduction does not make arbitrary legacy item payloads unlimited or guarantee an instantaneous export.
