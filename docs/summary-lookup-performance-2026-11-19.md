# SP/SPPH summary reads and SPPH PR lookup — 19 November 2026

The attachment status summary on each document list read matching item descriptions for every displayed document, even when an explicit requirement or existing attachment already determined its status. The SPPH PR options endpoint also differed from the hardened SP lookup: it did not validate search shape/length, trim whitespace, treat `0` as a real query, escape SQL LIKE wildcards, or send an explicit private/no-store response.

`ProcurementDetailService::summaries` still reads requirements and aggregated attachment counts fresh for the displayed IDs. It now reads item text only for IDs absent from both results. If every displayed document has a known requirement or attachment, summary reads decrease from **3 SQL statements to 2**, with no item descriptions loaded. Mixed pages retain three statements but narrow the item query to unresolved documents. The original combined description/item detection and negation rules remain for those documents. Existing attachment counts retain precedence over a deferred requirement; no OCR text or file content is loaded for summary generation. The optimization does not cache status, truncate legacy items or change search indexes.

The SPPH options lookup now validates `q` as a nullable string of at most 160 characters before SQL. It trims the term and uses a strict empty-string check, so `0` is searched. `%`, `_`, `!` and backslash are literal input, using bound LIKE parameters and an explicit `!` escape. The existing six-field Select2 DTO, descending PR ordering, 50-row limit, one-query budget and cancelled/already-linked exclusions are preserved. Responses are private/no-store, and eligibility is read fresh rather than cached. Existing authentication, department, read-only and isolated request-budget middleware remain unchanged.

Eight additional tests cover known and mixed summary pages, legacy rich text and cross-field negations, review/delete/defer freshness, empty pages and SP/SPPH ID isolation, malformed option input before SQL, literal/zero search, DTO/privacy, bounds, live eligibility and access control. Six assertions/scenarios failed on the old implementation before the fix (other baseline cases passed). The full PHP suite passes **993 tests / 11,038 assertions**, including 42 focused tests / 493 assertions. Pint passes on the four changed PHP files. No JavaScript or view code changes are included in this batch.

Fresh in-memory SQLite browser fixtures render the current SPPH page. Desktop/light and mobile/dark checks pass for number lookup cancellation/timeouts, escaped messages, retained draft/date, edit readiness, changing PR selections and retry actions. They perform no procurement writes. Server-side feature tests exercise the actual options endpoint; these browser fixtures check compatibility of the existing form behavior rather than claiming an authenticated production browser session.

The production baseline probe confirmed the extra item read on both modules. In the sampled recent ten-document pages, only **3 SP documents** and **5 SPPH documents** required item-text detection, although all ten were included in the old item query. Separate ten-document samples with known status required no item detection. Baseline option reads also reproduced result mismatches for `0`, `%` and `_`. These samples describe the data at audit time and are not a site-wide latency benchmark.

Candidate and deployed probes compare every summary state/label to the original implementation on recent, known-status and legacy samples, check item-query IDs and 0/2/3 statement budgets, and compare literal lookup results with independently constructed expected queries. They enforce a 50-row limit, narrow projection, unchanged DTO, private/no-store headers, zero SQL for malformed searches and the existing route guards. Probes use an explicit read-only database transaction, array cache/session and prevented external HTTP; they do not upload, review, approve, generate documents or change production records. Completion and zero-write markers are required.

Deployment is restricted to the two backend files, two test files and this document, from exact baseline `be02a3a75413472bea446fcdb666088e8d17ce7b`. The previous modified files and bootstrap cache are backed up privately. PHP lint and candidate checks precede the fast-forward; deployed checks, source hashes, `/up`/login health, unauthenticated SP/SPPH/options access and a clean tracked tree follow. No schema migration, public asset publication, route/config rebuild, new dependency or global cache flush is needed. This change reduces specific list work and corrects lookup behavior; it does not guarantee that all website operations are instantaneous or bug-free.
