# Archive upload streaming — 19 November 2026

`PrArchiveService::uploadDocument` previously read the entire source with `file_get_contents` before attaching it to the outgoing multipart request. This retained a file-sized PHP string while the HTTP client transmitted the same file. The shared method is used by the SP, SPPH and PPBJ archive attachment buttons.

The method now opens the uploaded temporary file in binary read mode and attaches that resource directly. A `finally` block closes the owned descriptor on successful creation/replacement, duplicate responses, upstream errors, transport exceptions and early returns. An unreadable or missing source returns the existing unavailable result before making an HTTP request. File format/size validation, metadata, bearer authentication, duplicate/replacement handling, success-only metadata cache invalidation and controller authorization remain in place. No extra query, copy, queue job or automatic write retry is introduced.

Outgoing upload requests no longer follow redirects. Previously Guzzle could follow 307/308 redirects and resend a private multipart body to another origin; it could also follow 301/302/303 and report the resulting unrelated successful response as an uploaded document. Production archive source inspection shows that its upload API directly returns JSON with 200/201 or a duplicate/error status. A redirected upload now returns the existing failed result and makes no request to the next destination. An intentional deployment redirect must therefore be resolved by configuring the canonical upload endpoint. This restriction applies to uploads; the separately validated OneDrive download redirect flow remains available. Transport exceptions are logged using the exception class without upstream messages that can contain credentials or local paths.

Thirteen added regression cases use the real Guzzle middleware with an offline `MockHandler`. Six outcome cases verify that the original file is an open `rb` stream during transfer, its SHA-256 is unchanged, the descriptor is closed on return, metadata/authentication are preserved and only confirmed success invalidates the metadata cache. Five redirect cases cover 301/302/303/307/308 and prove that the second queued destination is never requested. Additional cases check transport failure without an automatic retry, redacted diagnostics and a missing local source. The previous implementation failed twelve of these cases. Four existing request assertions now inspect exact multipart field values instead of trying to reread a deliberately closed source stream after the request completes.

The focused archive/upload/format/access set passes **75 tests / 562 assertions**. The complete PHP suite passes **1,041 tests / 11,843 assertions**. Production candidate/deployed checks are required before release. Pint passes on the service and both changed test files. This batch has no JavaScript, view, route, dependency or schema change.

A fresh-process loopback HTTP benchmark compares the actual prior service from commit `550df8d6b6cf33e278eebc1c9b56f9a6f9927581` with the candidate. The local receiving server parses the real multipart POST and checks authorization, file name, file hash and metadata. Both versions deliver the same **10,420,233-byte file**, use one upload request each and receive the same successful acknowledgment. Additional PHP peak memory above the warmed pre-transfer baseline decreases from **12,582,912 bytes (12 MiB)** to **2,097,152 bytes (2 MiB)**, approximately **83%**. This is PHP allocator memory for this synthetic near-ten-MiB upload, not total process/native cURL memory, the destination server's memory, all uploads or whole-site latency. Network throughput and remote OneDrive processing still depend on those services. Smaller transfers may still be buffered internally by the installed HTTP transport.

Deployment is limited to this service, two feature test files and this document. Modified tracked files and bootstrap cache are backed up privately before a fast-forward. Candidate and deployed production probes use a short-lived synthetic temporary file, offline Guzzle handlers, array cache/session and a read-only SQL transaction. They check six response states, byte hashes, descriptor closure, cache behavior, five blocked redirects, connection/missing-source failures, the canonical HTTPS upload configuration and authentication on all three upload routes. No real archive metadata lookup, remote upload or business mutation is performed. The synthetic temporary file is closed and removed by PHP. Exact source hashes, normal health responses and unauthenticated download guards are verified after deployment, along with a clean tracked tree. No migration, public asset publication or global cache flush is involved.
