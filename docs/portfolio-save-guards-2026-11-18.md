# SP portfolio mapping save guards — 18 November 2026

The portfolio-to-PR-field manager used for SP printing previously accepted any structurally valid mapping row as a save confirmation, including a different edited ID or different submitted values. After a timeout, unreadable reply or server failure, the same write could be submitted again without first loading the latest list. An edit rejected with a version conflict kept its obsolete version available for repeated attempts, and a failed list read could also show an empty-results message.

Confirmation now requires the returned row to match the edited ID, exact trimmed portfolio, selected field ID and active flag. Its field must still be available, and row text/types/version must satisfy the existing DTO contract. Until that confirmation, the draft remains. Connection/body timeout, redirected/HTML/unreadable replies, malformed acknowledgment and internal server failures mark the write unverified. Saving is blocked until a valid list read completes; failed or malformed reloads do not lift that guard. These are explicit user reads, without automatic POST retries or new polling.

A 409 edit conflict retains the draft, removes obsolete edit buttons and blocks the stale version. Reloading the list does not silently replace the edited fields or advance their version. The user must explicitly select Edit on a freshly loaded row, or abandon that edit, before another save. A confirmed save followed by a failed list refresh remains reported as saved. Closing an unverified result carries a verification notice to the next opening; departure during a confirmed write's follow-up read does not relabel that write as uncertain.

List responses must have consistent total/page/last-page/row counts, unique row IDs and bounded typed suggestion metadata. Failed reads display an unavailable-list state; only successful empty results claim no matches. Existing selected fields beyond the first fifty, local portfolio filtering, manual drafts, escaped messages, CSRF, read cancellation, thirty-second connection/body deadlines and no-overlap behavior remain. Known validation/access/session/rate rejections do not falsely claim successful saving. Error details are bounded strings, and internal details are suppressed.

Verification passes **614 JavaScript tests** and **972 PHP tests / 10,785 assertions**. Mapping tests exercise mismatched IDs/values/field availability, uncertain resubmission guards, failed and successful reloads, obsolete versions, explicit selection of the latest version, inconsistent lists, cancelled/departed reads, and confirmed-versus-unconfirmed departure. Existing tests retain versioned PUT, validation drafts, late replies, read-only access and failed post-save refresh coverage. Browser scenarios pass desktop/light and mobile/dark with real local UI libraries and synthetic endpoints; they check disabled controls, explicit retries, fields outside the initial dropdown page, preserved manual input, literal markup, wrong acknowledgments, malformed lists and stalled write bodies. Screenshots were inspected. No production mapping is written during these checks.

Deployment requires the exact prior commit and four-file allowlist, private application/bootstrap-cache/public-asset backups, staged and deployed read-only probes, atomic asset publication and fast-forward. The probes use an unsaved synthetic user, array cache/session, blocked outbound HTTP and a read-only database transaction. They verify the current DTO/version/privacy contracts, list bounds of twelve rows and at most three SELECTs (seven with initial suggestions), literal search and invalid-input/access/rate guards. Public SHA256, unauthenticated access and health checks repeat afterward. No backend, schema, route, view, runtime dependency or global cache flush changes are needed; existing untracked artifacts are excluded.

This strengthens one optional print-configuration workflow and avoids redundant or misleading client operations. The existing backend uniqueness, version and authorization checks remain authoritative. A successful list reload enables the user to inspect the outcome; it is not an exactly-once guarantee across users/devices. Drafts remain in the open popup and are not persisted across reloads. This is not a claim of site-wide latency improvement.
