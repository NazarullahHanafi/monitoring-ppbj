# SPPH edit data readiness — 18 November 2026

Previously, SPPH edit could save before its stored items finished loading or after an item-read failure, allowing an incomplete form to replace existing details. A failed stored-PR lookup converted the reference to manual, while late item failures could erase the contents of a different or reopened record. Initial PR hydration could also overwrite the saved or newly edited description. Vendor option detection used an interpolated selector that failed on names containing quotes.

Edit initialization now seeds stored PRs and vendors with literal option values, retains the document description, and tracks item and PR readiness independently. Stored links are selected before their metadata request, without triggering a second autofill request or clearing the description. Both reads use the existing twenty-second deadline/cancellation helper, including JSON body and uncooperative promises. A reply must still belong to the same record and edit generation, visible modal and, for PRs, the same selection and mode. Closing, changing forms or hiding the page cancels these reads through the existing lifecycle.

The submit path checks readiness before preparing attachments, showing the save simulation or making a business write. Loading/error states explain that the user must finish or explicitly retry the read. Adding item rows is blocked until stored items load, so an incoming result cannot erase items added while the original rows were pending. Failed item reads expose a **Cek ulang** action; successful retry restores the add-item control. Retrying PR metadata does not reload or erase the item editor.

Network failures retain stored PR selections and leave them in PPBJ mode. A known linked PR reported missing or cancelled requires review; it is not silently converted to manual. A legacy reference not declared as linked may still become manual after a successful server classification. Explicitly changing mode or selection cancels the obsolete hydration request. Stored descriptions and user edits are preserved while initial metadata loads.

PR selection checks in add/edit forms also use owned, bounded reads. Their reply must match the selection, current mode and edit generation. Error/paused reads expose an explicit retry. Edit saves remain blocked while a newly selected PR is loading or failed. Server messages are assigned as text, including linked/cancelled feedback, and the manual-PR warning escapes the typed number before building its dialog. Quoted vendor and PR values are compared as option values rather than interpolated CSS selectors.

The PR metadata endpoint now validates a maximum of twenty string references before querying, rejects malformed arrays instead of casting/truncating them, retains input order and deduplicates valid references. Literal `0`, percent and underscore references remain searchable. Every status response and the item endpoint use private/no-store headers. Empty metadata checks use zero queries; a valid batch uses one SELECT, including multi-PR requests. Items keep their single ordered SELECT, six-field DTO and existing rich-text sanitization. Existing access middleware and save-time validation remain in place. This work avoids stuck or incomplete client operations; it does not claim a whole-site latency improvement.

Verification covers stale and same-record item responses, item body deadlines, save/add-row guards, PR retry without losing item drafts, retained stored links/descriptions, legacy manual classification, changed selection/mode/generation, malformed item payloads and readiness before any write. Actual-page browser tests pass on desktop/light and mobile/dark using real local UI libraries and an in-memory SQLite-rendered view with synthetic API responses. They also exercise quoted vendors, new PR checks, literal message markup, timeouts and closing pending reads. No procurement POST is sent by those scenarios. Screenshots were inspected. Existing number-lookup, background and print-master browser regressions also pass. Full suites pass **576 JavaScript tests** and **967 PHP tests / 10,762 assertions**.

Production preflight compiles the staged view and exercises helpers in a read-only database transaction with an unsaved synthetic identity, array cache/session and blocked outbound HTTP. It rejects twenty-eight malformed requests across the metadata and prior lookup/poll paths without SQL, confirms zero/one-query metadata reads and one-query private item reads, and verifies the existing response contracts and access guards. The sampled production SPPH had no item rows; populated item ordering/sanitization is covered with isolated fixtures. No real account, SPPH, PR or vendor is mutated.

Deployment requires the exact prior commit, clean tracked tree and an eight-file allowlist. It backs up modified files and the published SPPH asset, validates staged PHP and read-only probes, fast-forwards and publishes the asset atomically. Public asset SHA256, health and unauthenticated access checks repeat afterward. There are no schema, route, view or runtime dependency changes and no global cache flush. Existing untracked user artifacts are excluded.
