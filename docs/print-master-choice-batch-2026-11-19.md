# Batched print master choices — 19 November 2026

The SP print popup previously fetched its selected signer, title and PR field in three independent HTTP requests. Each request used a paginator with a COUNT and a row query, giving six SQL reads when all three types contained active options. SPPH manual mode fetched two types in two requests/four reads. The manager's paginated search API was being used for dropdowns that only need their first fifty active options and the current selection.

The existing authenticated `/spph/print-masters` endpoint now also accepts a bounded `types[]` batch and a typed `include_ids` map. It reads up to fifty-one active records per requested type in independently limited derived queries combined with UNION ALL. A single outer query returns projected identity/name/active/version-source fields, with deterministic ordering and each applicable selected ID first. The fifty-first record detects truncation without a COUNT query. Output contains at most fifty rows per type, three types and 150 rows total, with explicit boolean truncation flags. Private/no-store responses and the existing department/authentication/rate guards apply. The legacy single-type search/pagination contract remains available for the manager and previously loaded clients.

The shared client sends one request only when choices are needed. It includes the current signer/title/field IDs, retains caller cancellation and a thirty-second connection/body deadline, and does not cache results, poll or automatically retry. Invalid stored identifiers fail before a request. The complete response is validated before exposing any group: exact expected type keys, numeric limit, array/row limits, matching types, active flags, unique IDs, typed versions/names and consistent truncation metadata. An incomplete group fails the whole read instead of letting a popup mix verified and unverified choices. Existing explicit server validation before preview still rechecks the actual selected active masters.

Seven new PHP cases exercise one-query budgets, all three groups, selected rows beyond the first fifty, exact parity with legacy results, inactive/wrong-type/missing selected IDs, empty groups, 50-versus-51 truncation, fresh version hashes, invalid or ambiguous parameters rejected before SQL, and guest/department/viewer access. Shared-client tests cover lazy one-request loading, invalid/partial/duplicate/inactive/oversized responses, invalid IDs, stalled bodies, cancellation and late data. Existing manager, save, version-conflict and print lifecycle coverage remains.

The full suites pass **985 PHP tests / 10,957 assertions** and **621 JavaScript tests**. Browser payment scenarios pass both modes on desktop/light and mobile/dark, checking exactly one choice read, retained drafts, cancellation without POST, one explicit confirmation and same-tab preview. SP/SPPH lifecycle scenarios on desktop and mobile preserve draft reasons, escaped validation feedback, body deadlines, changed-basis reconfirmation and close cancellation while using the combined helper. SPPH automatic mode still needs no choices until the user selects manual mode.

Read-only production probes confirmed the prior budgets of 3 requests/6 SELECTs for SP and 2 requests/4 SELECTs for SPPH choices. Candidate and deployed batches use **one request/one SQL statement**, with exact selected-first DTO/version parity against the legacy path. Each source is limited to 51 rows even for large tables. Probe validation uses process-local array cache/session, blocked external HTTP and a read-only SQL transaction; no master, user or procurement document is changed. Reported query reductions apply to choice loading, not the separate print context, master manager or entire website. The UNION statement still performs bounded work for each requested type; this is not a site-wide latency percentage claim.

Deployment requires the exact prior commit and seven-file allowlist, private application/bootstrap-cache/public-helper backups, PHP syntax checks and staged/deployed read-only probes. The additive backend is installed and checked before publishing the helper atomically. Controller hash, public helper SHA256, unauthenticated access and health checks follow. No schema, route, view, runtime dependency or shared cache flush is needed; unrelated untracked user artifacts are excluded.
