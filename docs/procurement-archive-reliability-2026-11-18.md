# SP/SPPH archive action reliability — 18 November 2026

The password-confirmed “Pindahkan ke Sampah” action previously had no write/body deadline or full operation ownership, and accepted any successful HTTP response as an archive confirmation. Repeated clicks could overlap requests, while incomplete JSON or a login response could produce a misleading success/navigation. Server validation messages were passed to SweetAlert as HTML.

A shared archive module now owns the operation before the existing read-only review and until completion. It accepts only a matching same-origin SP/SPPH numeric document URL. A second review or archive action cannot replace it. Its DELETE carries CSRF, same-origin credentials, JSON/XHR headers and no-store policy. The thirty-second deadline covers both fetch and body parsing, including promises that ignore abort. Password/reason controls and dialog dismissal are locked while the request is pending. The existing server permission checks, creator-password verification, three-attempt lock and rate limits remain unchanged.

Success requires a non-redirected JSON object with both `ok: true` and `archived: true`. A valid lock response must include bounded retry time and a parseable ISO lock timestamp. Validation/session/access/rate rejections display escaped feedback; internal failures do not expose server details. Connection/body failures, malformed success and uncertain responses stop resubmission within the dialog and expose links to the matching active list and Tempat Sampah. No write is retried automatically. The user must inspect those lists because aborting the client cannot undo a server-side commit.

Uncertain feedback preserves password and reason inputs. It updates only the affected controls rather than recreating the popup HTML. A guarded animation-frame update handles SweetAlert restoring its loader button after preConfirm; it cannot alter a replacement popup. Feedback and verification links stay readable in light/dark modes. Search snapshots remain frozen against password-manager noise and restore exactly once. Page departure aborts pending work, releases its cleanup and closes its owned dialog. Late replies cannot navigate or mutate a later operation. A missing helper on an older cached page asks for a reload rather than using the old write path.

Verification passes **608 JavaScript tests** and **972 PHP tests / 10,785 assertions**. New executable tests cover URL boundaries, ownership, CSRF, controlled retries after known rejections, stalled connection/body, incomplete/redirected/HTML replies, lock contracts, escaped feedback, verification links and departure/late results. Actual-page browser tests cover both SP and SPPH on desktop/light and mobile/dark, using in-memory SQLite-rendered views and synthetic DELETE replies. They verify one review/write on repeated clicks, preserved fields/search, locked controls/Escape, literal document/error messages, timeout/body handling, explicit verification, ignored old replies, lock countdown and navigation only after confirmed success. No production record is archived during testing. Screenshots were inspected. Existing SP/SPPH inline-vendor and SPPH vendor-usage browser regressions also pass.

Release uses an exact baseline and eight-file allowlist. Backups include modified application/views, bootstrap cache and prior public assets. The new helper is published before updated views reference it; SP/SPPH page scripts are published atomically. Staged and deployed read-only probes compile both views and verify dependency order/versioning, existing endpoint/access/cache contracts and eight invalid archive payloads rejected before SQL. They use unsaved synthetic models/identity, array cache/session and a read-only transaction, never a real archive request. Public SHA256 checks cover all three assets; health and unauthenticated read checks repeat afterward. No schema/backend mutation logic, runtime dependency or global cache flush changes are needed. Existing untracked artifacts are excluded.

This batch avoids redundant client operations and stuck/misreported archive actions. It does not claim a whole-site latency improvement or exactly-once server execution across devices. Uncertain outcomes require checking the existing lists before another manual action.
