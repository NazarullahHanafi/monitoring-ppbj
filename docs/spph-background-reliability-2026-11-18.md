# SPPH background updates and presence — 18 November 2026

SPPH background reads previously had no deadline and could hold their overlap guard indefinitely. Incoming records appended incomplete action cells and changed the count independently of pagination. Each incoming record also opened a SweetAlert toast that could replace an active confirmation. Presence heartbeats used intervals that could overlap on a slow connection.

This release replaces incoming-row insertion with one accessible notice and an explicit **Muat ulang daftar** action. Existing rows, complete server-rendered buttons, statistics and pagination stay together. Refresh is blocked while an add/edit form, procurement save, archive confirmation or SweetAlert is active, or while filters have changed without being applied. Incoming duplicate IDs do not inflate the notice, and its displayed count is capped at 1000+. Backend strings are not interpolated into notification HTML.

Network scheduling lives in `assets/app/procurement-background.js`, separate from the SPPH display adapter. The small reusable controller is instantiated only by SPPH in this release; existing SP behavior stays intact. Each read channel owns one request and one next timer. Initial list polling waits 45 seconds; presence waits 12 seconds initially, then 60 seconds after each completed read. Both connection and JSON body have a 20-second deadline, including uncooperative fetch/body promises. Failures back off to at most five minutes. HTTP 401/403/419 and login redirects halt automatic work until reload.

Hiding or leaving the page cancels reads and their timers. Old responses cannot mutate or unlock replacements. BFCache restoration schedules one timer per channel and retains failure backoff. Presence names use textContent, with at most twenty names displayed. Failed or paused presence hides its stale indicator. Start/stop writes serialize the latest desired action, use same-origin credentials and CSRF, and have a ten-second connection deadline. A successful heartbeat schedules its successor after fifteen seconds; failed writes back off to at most two minutes. Page departure cancels client work and attempts a stop beacon. A request that timed out may still complete on the server; the existing fifty-second activity expiry remains the fallback. No business save is retried by this controller.

The SPPH poll's new opt-in `summary=1` response selects only IDs in one SELECT, at most fifty rows, ordered by ID. Cursor and summary inputs are validated before SQL. Archived records remain excluded. Responses are private/no-store, and authentication, department and read-only middleware remain unchanged. Legacy clients retain all ten response fields, including multi-vendor labels, names and counts. Initial SPPH pagination already orders by descending ID, so its visible maximum ID remains the correct snapshot cursor without an additional MAX query.

Production preflight used a read-only database transaction, unsaved synthetic identity, array cache/session and blocked outbound HTTP. It rejected six malformed requests without SQL, verified one-query limits, DTO compatibility, soft-delete boundaries, view compilation and access guards. No production account, SPPH or vendor was changed. For the same fifty SPPHs, serialized JSON measured **501 bytes with summary versus 17,293 bytes with the legacy response**, about **97.1% less JSON payload**. This sample measures response size, not whole-site latency or a guaranteed page-load speedup.

Regression verification includes **957 PHP tests / 10,690 assertions**, **547 JavaScript tests**, actual-page SPPH desktop/light and mobile/dark browser scenarios, the existing SP background browser scenarios and print-master browser regressions. The browser tests use an in-memory SQLite-rendered Blade fixture, real local UI scripts and synthetic API responses. They exercise active dialogs, drafts, unapplied filters, unchanged rows and literal presence names; screenshots were inspected. Backend coverage includes malformed cursors, the narrow query, fifty-row continuation, maximum cursor, legacy multi-vendor fields, archived records, pagination cursor and access boundaries.

Deployment checks an exact previous commit, clean tracked tree and a ten-file allowlist, backs up modified files and the existing published SPPH asset, then validates staged code. The new shared asset is published before the view can reference it; the SPPH asset is replaced atomically. Blade uses normal timestamps. Post-deployment probes verify both public asset hashes, health and unauthenticated access. No migration, global cache flush, maintenance mode or shared presence-trait change is needed. Existing local untracked user artifacts are excluded from the release.
