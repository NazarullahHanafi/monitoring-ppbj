# SPPH number lookup reliability — 18 November 2026

SPPH add/edit number checks shared one debounce timer, accepted late responses without checking the current number/date/record, and could leave requests pending indefinitely. Suggestion labels interpolated the server's last number into HTML. Conflict recovery also used the add form's date when requesting a number for an edited document. This release addresses those number-check, suggestion and recovery paths.

Each number field now owns its debounce timer and request generation. Typing, clearing or changing its document date cancels the old check. Replies must still match the current number, date and excluded record before applying normalization or status. Add/edit checks do not cancel each other's timers. Requests use same-origin credentials, JSON headers, no-store and a twenty-second deadline covering both fetch and JSON body, including uncooperative promises. Closing a form, switching add/edit contexts, hiding the tab or leaving the page cancels outstanding lookup work. An owned lease prevents an old completion from unlocking a replacement. Failures show actionable text with an explicit **Cek ulang** button rather than silently clearing feedback or automatically retrying.

Suggestions validate their response shape, render last-number labels as literal text, and use real type=button controls. A suggestion only fills the input after an explicit click; old suggestion buttons cannot fill a number after the date or request generation changes. Messages and number strings cannot become HTML. Foreign lookup URLs are rejected before fetching.

Explicit conflict recovery reads the date belonging to the requested add/edit form. Before updating a number, it rechecks the draft number, date, form action, modal visibility, record ID and same-record edit generation. A changed or closed form keeps its current number. Recovery has the same bounded request lifecycle and never automatically resubmits a procurement save. The prior conflict classification behavior is unchanged.

Backend number/suggestion endpoints validate string lengths, calendar date format and nonnegative integer record IDs before querying. Valid older dates such as March 2025 retain their selected month/year; no new year restriction is imposed on the existing save-time unusual-date confirmation. JSON responses explicitly use private/no-store headers. Archived numbers remain reserved and the current record can still be excluded from edit duplicate checks. Existing authentication, department/read-only middleware and authoritative save validation remain in place.

SQL behavior is preserved: empty checks use zero SELECTs, a cold non-sequential check uses one, a warm check uses zero through the existing thirty-second application cache, sequence-aware checks use at most three, and suggestions use two. Lookup availability remains advisory because that application cache can briefly outlive a concurrent change; saving still performs its own uniqueness validation. This release reduces stale and stuck client work and adds request safety without claiming a whole-site latency reduction or removing all database work.

Verification includes twenty new JavaScript lookup/recovery tests, backend lookup tests, actual-page SPPH desktop/light and mobile/dark browser scenarios, plus the existing SPPH background and print-master browser regressions. The browser tests use the in-memory SQLite-rendered Blade fixture and synthetic API responses; no real procurement write occurs. They cover stale checks, escaped server markup, stalled response bodies, explicit retry, the edit date, changed drafts and cancellation after closing. Screenshots were inspected. Full suites pass **567 JavaScript tests** and **962 PHP tests / 10,730 assertions**.

Production preflight compiles the staged view and exercises lookup bounds in a read-only transaction using an unsaved synthetic identity, array cache/session and blocked outbound HTTP. It rejects twenty-two malformed inputs across the number and existing poll endpoints, verifies private responses, preserves the old selected-date normalization, and checks existing access guards and the prior poll DTO. It does not mutate production users, SPPHs or vendors.

Deployment requires the exact prior commit, clean tracked tree and a seven-file allowlist, creates a private backup, checks staged PHP/probes, fast-forwards and publishes the SPPH asset atomically. Public asset SHA256, health, unauthenticated access and probes run again after deployment. No new runtime dependency, route, migration or global cache flush is introduced. Existing untracked user artifacts are excluded.
