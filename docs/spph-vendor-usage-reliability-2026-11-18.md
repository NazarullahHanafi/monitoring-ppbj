# SPPH vendor usage reliability — 18 November 2026

Previously, a failed or unfinished vendor-statistics request was displayed as zero uses or a new vendor. The request could wait indefinitely, its response remained cached in the page for its entire lifetime, and reopening a form could reuse a cancelled/stale promise. The server could count one vendor twice in one SPPH when aliases differed only by repeated spaces.

The usage read now uses the existing same-origin, private, twenty-second lookup helper, including response-body deadlines and cancellation on close, form change, hidden tab or page departure. One owned operation serves concurrent callers. Cancellation releases ownership immediately so a reopened form can start a new read; late replies cannot replace it. Loading, failed and paused reads show that usage is unknown rather than claiming zero. Selected vendors and procurement drafts remain intact. An explicit **Cek ulang** button retries once at the user's request; there is no automatic retry or polling. Statistics failure does not block saving the SPPH.

Successful snapshots are reused for sixty seconds. Reopening a form after expiry refreshes the snapshot; it does not add a repeating timer. A response must contain a valid dictionary of nonnegative integer counts, consistent totals, bounded text/date fields and known status values before any counts are displayed. Empty dictionaries and legacy empty arrays are accepted. Dictionary lookup handles names such as `constructor` and `__proto__` safely. Vendor names, document numbers and hints remain text/escaped content. Counts in the selection and dropdown reflect unknown/ready state consistently. Returning to a paused tab exposes the retry without issuing another request.

Server responses now use a stable JSON dictionary, including `{}` for no statistics, and private/no-store HTTP headers. The existing one-hour application cache and 500-row database chunks remain. Counting deduplicates the same normalized vendor within each SPPH. Cache namespace v2 avoids reusing inflated v1 counts; every existing SP/SPPH controller invalidation now targets v2. The obsolete cache expires normally. There is no schema change, global cache flush or dependency change.

Verification: **599 JavaScript tests** and **972 PHP tests / 10,785 assertions** pass. New PHP scenarios verify dictionary/privacy contracts, two SELECTs on a small cold fixture, zero procurement SELECTs on a warm read, normalized alias counting, archived exclusion, latest usage, old-cache isolation, read permissions, rate limits and cache invalidation after actual isolated SP/SPPH saves. JavaScript scenarios execute the actual read and rendering code for shared ownership, TTL, connection/body deadlines, explicit retry, lifecycle cancellation, reopened reads, malformed/auth/rate responses, prototype-like names, literal markup and Unicode names.

The actual SPPH page passes desktop/light and mobile/dark browser scenarios with local UI libraries, an in-memory SQLite-rendered view and synthetic responses. They verify unknown-versus-zero, one concurrent read, malformed payload rejection, stalled JSON, retry, close/reopen, ignored old replies, cache reuse/expiry, escaped text, preserved drafts/selections and saving despite unavailable statistics. They send no procurement writes. Screenshots were inspected. Existing inline-vendor, edit-read and number-lookup browser regressions also pass.

Deployment uses the exact prior commit and a seven-file allowlist, private file/cache/asset backups, staged PHP syntax and read-only probes, a fast-forward and atomic SPPH asset publication. Production probes use an unsaved synthetic identity, array cache/session, blocked outbound HTTP and a read-only transaction; they validate the statistics payload and warm-query count without mutating vendors, real accounts or procurement records. Health, public asset SHA256 and unauthenticated endpoint checks repeat after rollout. Untracked user artifacts remain excluded.

This improves the accuracy and reliability of one optional read and avoids redundant concurrent requests. Warm-cache query measurements apply to the statistics controller, rather than total website latency including authentication, network and rendering. The cold rebuild still scans active SP/SPPH records in bounded chunks, and an already open form does not continuously poll for changes.
