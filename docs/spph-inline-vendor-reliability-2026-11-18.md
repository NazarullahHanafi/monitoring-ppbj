# SPPH inline vendor reliability — 18 November 2026

The SPPH add form previously allowed concurrent inline vendor POSTs and had no deadline for a stalled connection or response body. Cancel, reset, reopening add or opening edit could change the form while a vendor write was still pending. Success accepted incomplete replies, and a vendor name was interpolated into a SweetAlert HTML title. The inline email field also participated in native validation of its enclosing SPPH form, even when its panel was hidden.

Inline vendor creation now owns one operation at a time. It locks its profile fields, vendor multi-select, toggle, save/cancel buttons, enclosing submit and modal close controls while preserving their original disabled states. Add/reset/cancel/close/edit entry points and both layers of parent submission refuse to replace or save that pending form. Other SPPH draft fields remain usable. A thirty-second deadline covers connection and JSON parsing, including promises that ignore abort. Departure aborts the client operation and releases its controls; it does not imply rollback of an already received server write.

Required name, field lengths and email syntax receive inline text feedback and field focus before any POST. The email input retains a mobile email keyboard without triggering native parent-form validation. Status feedback has a live region. The request retains all eight vendor profile fields, CSRF body/header, same-origin credentials and the existing server-side validation, uniqueness, permissions and rate limits. It introduces no dependency, database query or schema change.

Confirmation requires a non-redirected JSON object containing a positive integer ID and the exact submitted trimmed vendor name. A reply may change the form only while its operation, generation, form action, visible modal, profile and selected vendors still match. Success appends the new vendor to **all** previously selected vendors, compares literal option values, avoids duplicate options and presents the name as text. Existing SPPH descriptions and items are not reset. Validation/auth/rate errors retain the profile with appropriate feedback. Unknown outcomes retain it and link to the vendor list for checking; no POST is retried automatically. Late replies cannot erase a newer draft or select an obsolete vendor.

Verification: **590 JavaScript tests** and **967 PHP tests / 10,762 assertions** pass. New executable JavaScript cases cover write ownership, custom validation, field errors, session/access/rate errors, stalled connection/body, malformed replies, departure, changed drafts/selections/actions, literal markup, deduplication, multi-vendor preservation and missing CSRF. Parent-save regression tests cover both SP and SPPH. Actual-page browser scenarios pass on desktop/light and mobile/dark using local UI libraries, an isolated in-memory SQLite-rendered view and synthetic responses. They check duplicate clicks, reset/cancel/close/reopen/edit guards, preserved selections/descriptions, no native dialogs, literal errors/names, body timeout and late replies, with zero SPPH writes. Existing SPPH edit-read and background browser regressions also pass. Both screenshots were visually inspected.

Production verification compiles staged and deployed Blade, checks inline email/status markup, existing access/rate guards and read endpoint contracts in a read-only transaction with an unsaved synthetic identity, array cache/session and blocked outbound HTTP. It performs no vendor creation or real account/procurement mutation. Release requires the exact prior commit and six-file allowlist, private backups, staged checks, a fast-forward and atomic publication of the SPPH asset. Public SHA256, health and unauthenticated access checks repeat afterward. No global cache flush is required; normal Blade timestamps invalidate the modified view. Untracked user artifacts are excluded.

This batch prevents duplicate client operations and avoids a stuck vendor form. It does not claim a site-wide speedup or guarantee that a timed-out POST was not committed; server-side uniqueness and explicit verification remain important.
